# idea-chat wire study (Phase 1)

Reference: `~/idea-chat` at commit `6437901` (crates `chat-api`, `chat-model`,
`idea-state`) and the `server` 3.0 crate source (`~/.cargo/registry`,
downloaded via the `crates.idealyst.io` index configured in `~/.cargo/config.toml`;
also `server-kit` 3.0.0 and `server-macros` 1.5.2). RWND is `discord-clone` +
`discord-server` on `server` 4.0.3.

One correction to the task text: there is no `discord-clone/src/backend/mod.rs`
in this repo (checked `main`, `b60-2-work`, and the full `--all` tree). The
backend "traits" are per-area wrapper modules in `discord-clone/src`
(`servers.rs`, `dms.rs`, `auth.rs`, `blocks.rs`, `friends.rs`, `moderation.rs`,
`pins.rs`, `reactions.rs`, `mentions.rs`, …) that call `discord_server::<area>::<fn>`
RPC stubs generated by `#[server]`, plus the `message_gateway` socket. This study
maps that surface — every RPC and gateway frame the client actually uses — which
is exactly what `IdeaChatBackend` must reproduce.

## 1. Call format

`#[server]` fns ride one fixed route; the wire name is the path segment under
`/_srv/` (`server-macros` 1.5.2 codegen: `path: fn_name` unless overridden).

- `POST /_srv/<fn>` — `Content-Type: application/json`
- Body: a **JSON array of the arguments in declaration order**, each serde-JSON.
  A `user: Auth<Principal>` trailing parameter is NOT sent — it is injected
  server-side from session auth. No args ⇒ body `[]`.
- Response `200`: the serde-JSON **return value** (not wrapped).
- Errors (`server-kit` 1.5.2 `ApiError`):
  `{"e":{"failed":{"message":"…"}}}` for `ServerError::failed`. Variants
  `failed`, `invalid`, `forbidden`, `unauthorized`, `unavailable`, `too_many_requests`
  carry a `{message}` object; `incompatible_version` is null. HTTP status:
  401 for `unauthorized`, 426 with an `x-srv-schema` header for version mismatch,
  400 otherwise.
- Schema gate: clients send `x-srv-schema: <hex>` (a hash of the fn's signature);
  a mismatch is refused 426 before the handler runs. `IdeaChatBackend` must either
  send the hash the running idea-chat build expects, or treat schema enforcement as
  optional and discover the value; note idea-chat's `chat-api` is not a dependency,
  so the hash cannot be computed client-side from source — get it from a live
  handshake or from Nicho.

Auth (`server-kit` 3.0.0 `sessions.rs`):
- Web: login sets an httpOnly/Secure/SameSite=Lax cookie named **`session`**
  (kit default; value = session token). Every subsequent call sends it in the
  `Cookie` header. The JS never sees the secret.
- Native: the caller announces itself with the `x-idealyst-client: native`
  request header; `sessions.start()` then returns `SessionTicket{token: Some(bearer)}`,
  stored in the OS keystore, sent as `Authorization: Bearer <token>`.
  One guard accepts cookie **or** bearer.

### Worked example: sign_in

idea-chat `auth.rs`:
```rust
#[server(tags(limit = "20/min"))]
pub async fn sign_in(email: String, password: String) -> Answer<Session>
```

```
POST /_srv/sign_in HTTP/1.1
Content-Type: application/json

["alice@example.com","hunter2"]
```
Success (the `Session` payload; on web a `Set-Cookie: session=…` header rides
along and `token` is null):
```json
{"user":{...},"token":null,"device":...}
```
Refusal:
```json
{"e":{"failed":{"message":"Those aren't our records. Try signing up?"}}}
```

`Answer<E>` is `Result<_, ApiError>` (`chat-api/lib.rs`), so every idea-chat fn
uses the kit error shapes above. `sign_in` never 401s — it tells the account
layer in plain text.

### Worked example: send

`messages.rs` `send(channel, body, …)` → `POST /_srv/send` body
`[{"space":...}, "hello"]`-shaped args in declaration order; the fresh
`MessageCreated` fact itself arrives on the live connection, not in the reply
(the reply answers the post slot, the connection explains the fact).

## 2. Live connection

`chat-api/live.rs` declares `#[server::channel] live(mut ch: Socket<Up, Down>, ticket: String)`.
`idea-state` fixes the frame protocol; `chat-model/live.rs` the payloads.

Ticket flow:
1. `POST /_srv/live_ticket [null]` (session-authenticated; optional device id arg)
   → a signed string `t1.<user-uuid>.<device|->.<expires_ms>.<hmac-sha256-hex>` (`srv.rs: check_ticket`).
   Good for ~1 minute, one connection, because a native WS open carries no headers.
2. Open `ws(s)://<base>/_srv/_ws/live` — the `server` 3.0 client helper appends
   the hex-encoded open args to the URL (`client.rs:180/206`: open args `["<ticket>"]`
   hex-encoded and appended); the server validates the ticket (`check_ticket`)
   and registers the connection's topics before taking a snapshot.

Frames are **JSON text**, one `Up`/`Down` enum per message (`idea-state/lib.rs`,
tag field `"t"`, snake_case constructors):

```json
// server → client, first frame:
{"t":"snapshot","seq":0,"state":{ ...chat_model::State... }}
// then per change, seq numbered PER CONNECTION:
{"t":"event","seq":7,"event":{"t":"message_created","message":{...}}}
// refusals and keepalive:
{"t":"refused","reason":"…"}
{"t":"pong"}
// client → server:
{"t":"ping"}
{"t":"action","a":{"t":"typing","channel":"<uuid>"}}   // Action tag field "a"
```

`Cursor::step` semantics (`idea-state`): event seq must be exactly `seen+1`;
`Duplicate` (≤ seen, from an overlapping resnapshot) is ignored, `Gap` means
throw state and wait for a fresh `Snapshot`. `Resync` events (`chat-model/live.rs`)
are server-internal: the handler re-snapshots and re-topics; a client never sends
one. `Down::Snapshot` is also re-sent when a `Resync` fires (`live.rs` server loop).
Connection lifecycle doubles as presence: first socket of an account brings it
online, last close takes it offline.

Actions are fire-and-forget — `Typing` and `Idle` only. Everything that changes
stored data goes through the API so it can have a reply.

## 3. Uploads (`files.rs`)

```
begin_upload(name, size, content_type, purpose) → Slot{id, put_url, content_type}
PUT <put_url>                                    (presigned, ~10 min, send Content-Type)
finish_upload(id, width?, height?)               → Attachment{url, …}
send(..., attachments=[id])                      or set_avatar(id) / set_space_icon(space, id)
```
`purpose` is `message|avatar|icon`. Files are fetched at `Attachment.url`
(`/f/<key>` → short-lived signed redirect; the key is the capability).
Maxes: `MAX_UPLOAD`, `MAX_IMAGE` (`srv.rs`); 60 uploads/min.

RWND's flows map onto this directly (avatar upload, server icon) but not its
inline base64 attachments — see the table.

field for it); "adapt" = a call exists but shape or semantics differ.

## 5. Type mapping

| RWND (discord-server wire) | chat-model | notes |
|---|---|---|
| ids: `i64` (server/channel/message/user/dm) | `chat_model::Id` = Uuid v7, serde as **string** | biggest seam; see §6 |
| `ServerSummary{id,name,icon_url}` | `Space{id,name,icon,role,…}` | icon is `Option<String>` |
| `ChannelSummary{id,name,kind,position,parent,private,…}` | `Channel{kind: Text/Voice/DM/Group, parent_thread, archive, can_*…}` | RWND's `kind: String` vs typed Kind; permission booleans vs RWND's permission-bitsets (`PermissionSet`) |
| `DmMessage`, gateway `Message` | `Message{author, body, reactions:Vec<ReactionTuple>, attachments, flags}` | RWND carries `mentioned_user_ids` (resolved server-side); chat-model has no mention field — client parses or event-derived; RWND carries `embeds`, chat-model has none |
| `MemberInfo{user_id,username,display_name,role,avatar_url,presence}` | `Member{user_id,role:Role}` + `User{handle,display_name,bio,avatar}` + `presence()` derived | presence is a derived view in chat-model, not a member field |
| `Invite`/`InvitePreview` | `Invite{id,space,code,creator,expires,max_uses,uses,preview}` | nearly 1:1 |
| `Status` (online/idle/dnd/invisible) | chat-model `Status` (Online/Offline/Idle/Away — no DND, no Invisible) | **no RWND counterpart for dnd/invisible; no idea-chat status that hides a user** |
| `Role` string (member's role name) | `Role` enum (Member/Moderator/Owner) | **RWND's free-text custom roles have no counterpart** |
| attachments: base64 inline `AttachmentInput` (≤2 MB, ≤4/msg, server-resized `Image`) | upload triplet → `Attachment{url,width,height}`; `Flags` (spoof,nsfw) | RWND has no flag concept; idea-chat has no inline-bytes path |
| reaction tuples `(emoji,count,mine)` | `ReactionTuple(emoji,count,mine)` | identical shape |
| `WsServerMsg`/`WsClientMsg` (own framing, `seq` per frame from process-wide counter) | `idea_state::Down/Up` (seq per connection, gap detection → Resync) | frame vocabulary replaces per-socket queue; RWND's `History`-as-frames becomes API `history` replies |
| `WsServerMsg.MessageEmbeds`, `EmojiChanged`, `DmChanged` | no events | no counterparts either way (RWND-only features) |
| chat-model-only: `VoiceState/Ring/KeyRequest/SealedKey`, `Categories`, `Thread`, `Flags`, `Devices`/`EnrollToken`, `Relation{Friend,Following,Follower,PendingRequest}`, `Me`, `Failure` | RWND: `ServerSettingsResult`, `ChannelResult`, `MemberResult` (mutation-result echo structs), `Permissions` bitsets, `Overwrite`s | neither side has the other's |

## 6. Id plan

`IdeaChatBackend` keeps a client-side `Uuid ↔ i64` table ("first seen, first
numbered"), so the UI and its persisted `i64` state keep working. Things that
break or need care:
- **Uuids appear in URLs**: live tickets carry the user uuid (`t1.<uuid>…`),
  file keys are random, `put_url` is presigned opaque — all pass through
  untranslated (the i64 table never touches them). Fine, but the ticket's uuid
  must come from the table consistently with `whoami`.
- **Persisted last-view ids** (`last_viewed_message`, pinned ids, saved
  drafts): stored as RWND i64s in client state and server DB. An i64 table is
  per-session, so persisted i64s from a previous session won't resolve — the
  bridge must persist the table itself (localStorage/IndexedDB on web, SDK
  storage on native) or drop persisted-id features until Phase 2 moves ids to
  Uuid end-to-end. Flag: robot tests that assert ids (`messages::` suite,
  e2e's "Load earlier messages pill") assume stable ids across reloads.
- **Table must be stable across connections and users.** Two connections seeing
  the same space must number it the same — seed from a canonical order (e.g.
  snapshot order of a fresh session) or persist; otherwise two browser tabs
  diverge.
- `mark_read(channel,last_read)` and `Window::Before{id}` take Uuid ids on the
  wire: translate at the boundary, translate back for event application
  (`Duplicate`/`Gap` on `MessageDeleted { channel, message }` needs the reverse map).

## 7. Open questions for Nicho

1. **Roles.** chat-model has exactly three ranks (`Owner`, `Moderator`, `Member`,
   `Rank` in `spaces.rs`); RWND's role system is arbitrary named roles with
   per-role bitsets (`server_roles.rs`). Does idea-chat plan to grow
   custom roles, or is RWND's rich role UI expected to degrade to three?
2. **Accounts.** Signup is email+password with an email-verification code
   (`verify_email`, `resend_code`, `forgot_password`/`reset_password` — the "code"
   half looks WIP: no way to deliver a code to a client that just asked). RWND's
   is username/password. Which account model ships on idea-chat, and does the
   web signup really require an out-of-band email (no `send me the code` RPC)?
3. **E2EE** (`chat-model` mentions E2EE devices/`EnrollToken`/`KeyDelivered`):
   RWND has no counterpart. Is voice/call `KeyRequest`/`SealedKey` machinery E2EE-adjacent,
   and is it intended for RWND at all?
4. **Handle rename** — absent from `auth.rs` (looks unfinished: `handle_available`
   exists but no rename). Is username change planned?
5. **Link previews / embeds** — no model, no event. If RWND keeps them, where
   do previews live (server-side fetch is a security surface — link previews
   need SSRF policy; idea-chat has none).
6. **Pins, unread counts, notification settings, bans/timeouts, custom emoji,
   GIFs, channel permissions** — all RWND-only today. Are these deliberately out
   of idea-chat's scope (then `IdeaChatBackend` reports them unsupported and the
   UI hides the controls) or Phase-2 additions?
7. **Schema gate** — how should a foreign client obtain `x-srv-schema`? Is
   omitting it allowed (no header seen = what?), or should idea-chat expose a
   schema-discovery endpoint?
8. **`chat-api/lib.rs` is a WIP surface** (e.g. `set_muted` is one call for
   "channel or space" but `MutedChanged{target,muted}` gives no kind;
   `update_channel` takes `Option<Archived>` — archive-only, name via separate
   call). Anything planned but not written yet that RWND should code against anyway?
9. **Presence vocabulary mismatch**: chat-model `Status` has no DND and no
   Invisible; `PresenceChanged` carries "online/offline/idle/away". RWND's four
   statuses need a policy (DND→online? invisible→offline?) before any UI copy is final.
